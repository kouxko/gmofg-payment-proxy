## 背景

多个 Agent 同时执行任务登记或归档时，现有“扫描最大编号后创建文件”的流程存在扫描与写入之间的
竞争窗口，可能产生重复任务编号、重复文件名、待办入口冲突和完成索引冲突。

## 需求确认记录

- 用户确认采用一把全局锁串行化任务管理操作。
- 只考虑同一工作区内多个 Agent，不考虑多个 worktree、不同仓库副本或跨机器协调。
- 保留现有 `TASK-YYYYMMDD-NNN` 顺序编号，不改用 UUID。
- 任何任务的 Git 提交、提交历史、Commit ID、`git status` 或 `git diff` 都只用于变更管理和追溯，
  不属于验收结果，也不得证明功能正确、测试通过或任务完成。
- 并行执行的小任务必须等待同批全部结束并完成集成验证后，才决定是否执行一次可选的批次对抗审查。

## 目标

- 在 `AGENTS.md` 规定全局任务锁的位置、获取方式、持锁范围、等待方式和遗留锁处理规则。
- 覆盖任务创建、编号、目录、待办入口、完成归档、完成索引、测试索引和一致性验证。
- 普通源码实现不占用任务锁，只串行化任务管理元数据操作。

## 不在范围

- 不新增任务管理脚本或运行时代码。
- 不处理多 worktree、跨机器或多个 clone 的任务协调。
- 不修改现有任务编号和目录。
- 不 Push，不执行 CI。

## 最小改动与最优设计

| 方案 | 结论 |

| 只补充“主 Agent 分配编号”文字 | 无法约束多个独立 Agent，不采用 |

| 引入 UUID、中心服务或跨 worktree 注册表 | 超出已确认范围，不采用 |

- 检查锁规则包含原子获取、完整事务范围、等待、释放和遗留锁处理。
- 检查明确不考虑 worktree 和跨机器。
- 检查编号规则保持不变。
- 检查文档差异、链接和任务索引一致性。
- 任务管理完成证明只使用当前权威文件、索引关系、锁状态转换和复测输出；关联提交仅作追溯。
