## 背景

用户经常提供证书、URL、Host、Port 或临时配置，要求快速确认资源是否可解析、目标是否可连接或 TLS
是否可以握手。现行规范只定义了正式任务测试证据，缺少不修改源码、不做正式验收的轻量验证入口，
容易出现以下问题：

- 将两个独立连接测试合并描述成完整 Proxy 链路成功。
- 未保存实际使用的精确配置、原始资源、命令和输出。
- 临时 Workspace、Listener 或进程未完全恢复，却描述为清理完成。
- 把证书解析、TCP、直接 TLS、Proxy 上游测试或应用响应混成一个“配置可用”结论。
- 快速验证发现能力缺口后，没有明确升级为正式任务并引用原验证材料。

本任务以 2026-08-25 的证书与后台配置验证会话为具体反例，建立轻量、分层、可复测且不会冒充正式
验收的快速配置验证流程。

## 目标

- 定义快速配置验证的进入条件、权限边界、停止条件和正式任务升级条件。

- 强制先固定目标、证书角色、SNI、校验方式、允许的请求边界和成功标准。
- 分开报告资源、DNS、TCP、直接 TLS、Proxy 上游、下游 Listener、完整 Proxy 链路和应用协议结果。
- 保存实际证书、配置、命令、输出、清理状态和复测入口。
- 提供可以直接复制使用的快速验证模板和独立查询索引。

## 最小改动与最优设计

| 方案 | 结论 |
| --- | --- |
| 只在现有测试章节追加一句“快速测试可以简化” | 修改最少，但没有编号、证据格式、结论边界和升级条件，不采用 |
| 把每次证书或 URL 验证登记为正式 TASK | 复用现有结构，但流程过重且会把观察性验证与功能验收混淆，不采用 |
| 新增独立 QV 通道，复用全局锁、证据目录思想和分层结论，正式任务只引用不覆盖 | 既保留复现能力又避免冒充验收，采用 |

最优设计不增加产品执行脚本或产品依赖，只增加一个明确的观察性验证类型；一旦发生源码、持久配置、
业务请求或正式验收要求，立即进入既有任务流程。治理验证使用证据目录内的可重复状态场景脚本，不
进入产品运行路径。
