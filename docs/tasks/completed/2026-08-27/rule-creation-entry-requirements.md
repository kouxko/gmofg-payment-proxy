## 背景与目标

用户在统一规则页面先创建空白规则，再从“新建规则”选择 Socket 报文规则时，右侧没有进入可编辑状态。
只读排查确认当前 Workspace 没有符合 Socket 报文规则要求的协议入口；创建流程仍展示可选项，随后因
可用 Listener 列表为空而静默停止，页面只保留通用占位提示。用户进一步提出：空白规则选择可能不需要，
而需要绑定具体 Listener 的规则在没有兼容 Listener 时不应允许无意义创建。

目标是统一规则创建入口、可用性提示和运行时绑定语义，使用户只能进入具备明确执行归属的创建流程，
且无法创建时能够直接看到准确原因。

## 问题与根因分析

### 实际现象与环境

- 规则页面先选择“空白规则”，再次新建并选择 Socket 报文规则，右侧没有显示可编辑表单。
- 当次选中 Workspace 只有 HTTP plain 入口，没有 Socket scripted 入口，也没有 HTTP protocol Body 入口。

### 预期行为及依据

- 每条可执行规则必须具有明确运行归属；创建前置条件不满足时应直接阻止并说明原因，不能进入无草稿、无错误的伪创建状态。

### 最小复现

1. 选择只有 HTTP plain Listener 的 Workspace。
2. 进入规则页面并点击“新建规则”。
3. 可先选择空白规则，再次打开新建；也可首次直接选择 Socket 报文规则。
4. 选择 Socket 报文规则。
5. 实际结果：路由进入 Socket 创建模式，但因兼容 Listener 数量为零而不生成草稿；右侧显示通用占位文本。

### 当前已验证

- `protocolRuleListeners` 只接受 HTTP `body_processing.mode=protocol` 或 Socket `processing.mode=scripted` 的 Listener。
- 报文规则创建在兼容 Listener 为空时直接返回。
- 统一创建弹窗不检查兼容 Listener，仍展示 Body/Socket 选项。
- `editorOnly` 路径隐藏了报文规则列表原有的“当前工作区没有可配置报文规则的协议入口”提示。

### 推断

- “先点空白规则”不是根因，只是让用户更容易观察到从普通规则编辑器切换到无可用协议入口的状态。
- 核心缺陷是创建入口可用性与实际创建前置条件不一致，并且失败原因在统一编辑布局中丢失。

### 未知

- 无需求边界未知项；具体旧数据存储位置与删除触发点在实现前通过源码和测试进一步确认。

### 已确认根因与影响范围

- 根因：创建弹窗不感知兼容 Listener；报文规则控制器在无 Listener 时静默退出；统一页面又不渲染原有前置条件告警。
- 影响：Body/Socket 新建入口、普通规则与报文规则之间的状态切换、创建入口提示及相关集成测试。

## 最小改动与最优设计比较

| 方案 | 设计与影响 |
| --- | --- |
| 最小改动 | 删除空白规则类型和创建入口；创建项按兼容 Listener 禁用并说明原因；所有新规则保存单 Listener 绑定；删除已有未绑定普通 HTTP 规则。若现有模型可直接表达该合同，此方案范围最小且不保留兼容债务。 |
| 最优设计 | 由统一创建能力模型提供规则类型、兼容 Listener、不可用原因和绑定要求，并让创建弹窗、编辑器和保存校验共同消费同一合同，避免多处重复判断。 |

实现时优先复用现有能力与校验边界；若局部条件会复制 Listener 兼容规则，则采用统一能力模型，但不扩大规则执行语义。
