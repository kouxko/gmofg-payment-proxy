## 背景与目标

用户观察到支付应用已经收到正确响应、代理也完成双向转发后，抓包页面仍在“结果”列显示黄色“连接中”。
当前代码的一条 Exchange 对应一个 App Connection；长连接未出现 `closed` 事件时显示“连接中”，该值描述
连接生命周期，不是支付交易结果。但通用“结果”列、黄色状态和“最终结果”帮助文案容易被理解为交易尚未完成。

目标是在不推断支付业务结果、不改变连接生命周期的前提下，把现有状态明确表达为连接状态：

- 未关闭：`保持连接`；
- 正常关闭：`正常结束`；
- 错误关闭：`异常结束`，并继续展示原始错误。

## 范围

- 将抓包列表“结果”列改为“连接状态”。
- 将连接级展示统一为“保持连接 / 正常结束 / 异常结束”。
- 活跃长连接使用正常状态颜色，不再以黄色警告暗示交易未完成。
- 同步 Exchange 详情中的关闭事件说明和抓包页面帮助文案。
- 增加活跃、正常关闭、异常关闭三类前端回归测试。

## 不在范围

- 不新增“交易成功”“支付成功”或其他协议业务结果字段。
- 不根据收到/发送/失败计数、报文字段或 HTTP 状态自行推断业务结果。
- 不修改 Rust Exchange、Observation DTO、生成类型、数据库或协议包合同。
- 不改变 Listener `read_timeout`、Socket 长连接空闲策略、TLS `close_notify` 或连接关闭行为。
- 不通过主动关闭 App Socket 让页面进入“正常结束”。
- 若实际运行在空闲约 70 秒后出现 `READ_TIMEOUT`，应另行登记运行时超时合同任务，不并入本任务。

## 问题与根因分析

### 实际现象与环境

- 支付应用已收到响应，代理抓包记录已有完整双向收到/发送事件。
- Socket 保持长连接时，列表“结果”列显示黄色“连接中”。
- 连接后续若因读取超时或读取错误关闭，同一列显示“失败”，容易被理解为已经完成的交易失败。

### 预期行为及依据

- 一条抓包记录对应一个 App Connection，列表必须展示连接状态而不是未建模的支付业务结果。
- 活跃长连接是正常状态；正常关闭与异常关闭必须分开。
- 转发事件和异常错误继续如实保留，不新增业务推断。

### 最小复现

1. 构造一条 Socket Exchange：包含 `opened`、一组 upstream received/sent 和 downstream received/sent，不包含 `closed`。
2. 打开抓包列表。
3. 当前结果：通用“结果”列显示黄色“连接中”。
4. 预期结果：“连接状态”列显示正常色“保持连接”。
5. 分别追加 `closed outcome=completed` 与 `closed outcome=failed`，预期显示“正常结束”与“异常结束”。

### 当前已验证

- `ExchangeObservationRecord` 是连接级模型，一条记录对应一个 accepted App connection。
- `finalOutcome()` 只检查最后一个 `closed` 事件；无关闭事件返回“连接中”。
- 列表表头当前为“结果”，并把“连接中”映射为 warning 色。
- 详情当前直接显示原始 `completed/failed` 值；帮助文案使用“最终结果”。
- 当前 Observation 没有协议无关的支付交易成功字段，也没有 Interaction 级结果合同。

### 推断

- 状态值本身遵循连接级模型，但 UI 标题、颜色和帮助文案没有明确该边界，造成连接状态与业务结果混淆。
- 单纯增加“交易成功”文案会引入没有后端证据支持的第二套业务状态，超出最小修复范围。

### 未知

- 当前具体运行是否在空闲约 70 秒后出现 `READ_TIMEOUT`；该事实不影响本任务的 UI 语义修复，但决定是否需要后续运行时任务。

### 已确认根因与影响范围

- 根因：连接级 `closed` 状态被投影为通用“结果”，且活跃连接使用警告颜色，导致用户把连接生命周期误读为交易生命周期。
- 影响：抓包列表状态列、Exchange 详情关闭事件、抓包帮助文案及对应前端测试。

| 方案 | 设计与影响 |
