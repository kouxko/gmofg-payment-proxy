## 背景与目标

当前 Release App 启动即退出。直接运行 bundle 可执行文件得到明确错误：程序期望数据库版本 `22`，本机默认数据库标记为 `21`。此前统一规则任务规定旧数据库只 fail-closed，不自动清理，因此启动 hook 返回错误并由 Tauri panic 终止。

用户现确认新的产品合同：数据库版本 `100` 对应产品 `1.00` 正式版本基线；所有 `<100` 数据均为正式版前开发数据，启动时直接清空并按 `100` 重建；从 `100` 开始，后续 Schema 变化必须通过显式兼容迁移处理，不再清空。当前旧程序遇到 `>100` 的未来数据库继续 fail-closed。

目标是让当前本机版本 `21` 数据自动重建为版本 `100` 并正常启动，同时建立未来兼容迁移的明确边界。

## 范围

- 将当前应用数据库 Schema 版本固定为 `100`，并记录其为产品 `1.00` 正式基线。
- 启动发现有效 Schema 标记 `<100` 时，清空当前应用数据库并按当前 Schema `100` 原子重建。
- `=100` 时保留所有数据并正常打开。
- `>100`、缺失/重复/损坏 Schema 标记及非数据库文件继续 fail-closed，不得清空。
- 清理必须在同一 SQLite 事务内删除全部旧用户 Schema 和数据，确保已提交 WAL 状态也被纳入重建，
  不允许旧表或旧行重新进入新 Schema；本任务不承诺物理安全擦除磁盘页。
- 更新持久化架构/操作文档，说明 pre-1.00 清理与 post-1.00 显式迁移合同。
- 构建并启动本地 Release App，验证默认数据目录从版本 `21` 进入 `100` 后稳定运行。

## 不在范围

- 不实现尚未定义的 `100 -> 101+` 具体业务迁移。
- 不允许当前程序打开或改写 `>100` 的未来数据库。
- 不对缺失、损坏、伪造或多行 Schema 标记猜测为旧开发库。
- 不保留 `<100` 数据内容，也不提供旧开发数据转换。
- 不修改 HTTP/Socket 规则执行、代理协议或 UI 功能。

## 问题与根因分析

### 实际现象与环境

- macOS Release App 打开窗口后直接退出。
- bundle 可执行文件退出码为 `1`，Tauri setup panic 报告：`数据库结构版本无效：当前版本 22，实际标记 [(1, 21)]`。
- 默认数据库为 `~/Library/Application Support/com.interceptproxy.desktop/intercept-proxy.sqlite3`。

### 预期行为和依据

- 用户确认版本 `100` 是 `1.00` 正式基线。
- 合法 `<100` 开发期数据库必须清空并以 `100` 重建，应用随后正常启动。
- 正式基线数据不得因版本不匹配被静默删除；未来升级使用显式迁移。

### 最小复现

1. 创建带有效单行 Schema 标记 `21` 的当前结构数据库。
2. 启动 Host/Tauri Application。
3. 当前实现返回 `InvalidSchemaVersion { current: 22, found: [(1, 21)] }`，Tauri setup panic 后退出。

### 当前已验证

- 退出不是前端空白、WebView 或代理端口问题，而是 Host 初始化前的数据库版本拒绝。
- 使用独立 App identifier 和全新数据目录时，当前 App 可稳定运行并监听 `8765`、`17653`，证明二进制和前端 bundle 可启动。
- 当前 Schema 常量为 `22`，版本验证在 SQLite 初始化早期执行。

### 推断、未知与候选原因

- 已确认根因：正式前 Schema 版本变更与旧的 fail-closed 合同共同导致默认数据目录拒绝启动。
- 未知：无影响本任务实现方向的未知；精确清理事务边界通过源码和 RED 测试确定。

### 根因与正确修复边界

正确边界是在 SQLite 持久化初始化层识别合法单行 `<100` 标记，通过单个事务删除全部旧用户
Schema 和数据并按版本 `100` 重建；不能在 Tauri/UI 层吞掉错误，也不能把缺失、重复、损坏或未来
版本当成可清理旧库。

## 最小改动与最优设计比较

| 方案 | 分析 |

| 手工删除本机数据库 | 只能临时恢复当前机器，不能建立 1.00 产品合同，也无法保护未来用户，拒绝。 |
