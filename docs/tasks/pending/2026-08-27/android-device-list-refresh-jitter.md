## 背景与目标

用户观察到设备网络页面的“目标设备”下拉框持续抖动刷新。只读分析确认页面每秒无条件刷新 ADB
设备列表和运行所有者；每次 `devices.refresh()` 都把查询状态切换为 loading，而下拉框把
`devicesLoading` 直接映射为 disabled，导致控件每秒执行一次启用/禁用样式切换。

目标是在保持已经确认的设备发现及时性和操作安全边界前提下，消除后台刷新造成的可见抖动，并保证
设备选择、离线状态和手动刷新结果仍准确。

- 保持 ADB 设备列表、运行所有者、当前选择和离线设备合并逻辑的正确性。

## 问题与根因分析

### 实际现象与环境

- 设备网络页面已选择 A920MAX，“目标设备”下拉框持续周期性抖动。
- 当次 ADB 可稳定识别 A920MAX 和 IM28；页面没有设备网络运行所有者记录。

### 预期行为及依据

- 后台状态刷新不应让已有有效设备选择周期性失去可交互状态。
- 只有首次尚无快照、ADB 不可用、没有目标设备或真实冲突操作进行中时，才应显示对应不可用状态。

### 最小复现

1. 连接至少一台 ADB 在线设备并进入设备网络页面。
2. 选择目标设备，不启动设备网络接管。
3. 保持页面静置超过一秒。
4. 实际结果：每次设备列表后台刷新时 Select 短暂变为 disabled，形成周期性视觉抖动。

### 当前已验证

- `useAndroidOwnerRefresh` 每秒依次调用 `refreshDevices()` 和 `refreshOwners()`，不要求存在运行所有者。
- `useIpcQuery.refresh()` 在每次刷新开始时无条件设置 `isLoading=true`，完成后恢复为 false。
- `DeviceControlCard` 把 `devicesLoading` 直接纳入目标设备 Select 的 `isDisabled` 条件。
- 截图环境没有运行所有者，因此只在存在所有者时启用的运行状态轮询不是本次主因。

### 推断

- 抖动是后台查询状态错误映射为交互禁用状态造成的表现层回归；设备数据本身可以保持不变。

### 未知

- 无需求边界未知项；通用查询 Hook 是否必须调整由实现前影响分析确定，若会扩大到公共状态合同则重新确认优先级。

### 已确认根因与影响范围

- 根因：设备列表后台轮询、通用查询 loading 状态和 Select disabled 状态被直接串联。
- 影响：设备网络页面目标设备选择器、刷新按钮状态及相关轮询测试；不涉及 Android Companion 数据面。
