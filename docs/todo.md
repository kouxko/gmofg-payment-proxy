## TODO-SOCKET-CAPTURE-004：让 Socket 透明转发流量进入抓包 UI

需求状态：`待实施`

优先级：`P0`

### 已确认的问题与根因

- 透明转发当前走 `relay_bidirectional_with_progress`，只累计应用→上游服务、上游服务→应用的
  字节数并发布运行诊断，没有创建或注入 Socket 抓包上下文，因此抓包查询、事件刷新和详情 UI
  都没有可展示的数据。这不是前端刷新问题。
- 按协议转发和本机应答会经过协议处理器及现有抓包发布器；透明转发刻意绕过协议包、字段结构、
  规则与协议视图，所以不能复用现有“转发报文/本机应答”数据模型伪造一条协议报文。
- TCP `read`/`write` 的分段不是业务报文边界。一次读取可能只包含半条消息，也可能包含多条消息；
  UI 必须明确显示“字节流片段/连接流量”，不能把内部缓冲区边界称为报文。

### 目标设计

- 在 Socket 抓包模型中新增严格独立的 `TransparentFlow`（名称可在实现时按仓库约定调整）变体，
  与按协议转发、本机应答保持 closed union 隔离。该变体只保存：工作区、入口、运行代次、连接、
  双向序号、方向、已成功写出的原始字节、字节数、截断信息和时间；不包含协议包、字段结构、
  字段值、命中规则或协议视图。
- 在 proxy 的通用字节泵中定义中立、只读的“成功写出字节观察”接口；proxy 不依赖 application、
  SQLite 或 UI DTO。infrastructure 负责把观察事件适配到现有有界、非阻塞的抓包发布器，保持依赖
  倒置并避免把持久化逻辑塞进转发核心。
- 只在字节已经成功写入对端后记录对应范围。仅从源端读到但没有写出的字节不得出现在成功流量中；
  部分写入后失败时只记录实际写出的前缀，并保留关联的失败诊断；EOF 或空读取不创建空记录。
- 透明转发仍是完全透明的 byte-for-byte 路径：抓包观察不得调用协议包、Rhai、字段规则或协议视图，
  也不得修改、等待持久化或重新分块线路数据。SQLite 慢、抓包队列满或 UI 未打开时仍优先保证转发；
  若观察数据因有界容量被丢弃，必须提供可见的丢弃计数/诊断，不能静默制造“没有流量”的假象。
- 抓包列表按连接聚合展示双向累计字节和最近时间；详情按连接、方向和序号展示有序的字节流片段，
  默认提供 Hex/原始字节视图。产品文案使用“应用→上游服务”“上游服务→应用”“透明转发流量”，
  不显示 `Listener` 等实现术语，也不提供不存在的协议字段视图。
- 清空抓包、切换工作区和运行代次继续复用现有 generation/owner 边界；旧连接的迟到观察不得在清空后
  复活，也不得混入新入口运行代次。

### 实施边界

1. proxy：在双向 copy/write 成功边界发布有序观察事件，并保持 half-close、超时、取消和背压语义不变。
2. infrastructure：为透明转发注入抓包适配器，复用现有有界发布队列和 SQLite drain；新增透明流量
   持久化、分页、详情和清理实现。
3. application/Tauri：扩展严格 tagged union、分页/详情 DTO 和事件投影；透明流量字段不得借用协议包字段。
4. frontend：在现有 Socket 抓包列表和详情中增加透明流量分支、双向字节统计及 Hex 视图；按协议数据
   的协议视图和规则命中展示保持不变。

### 验收测试

- 真实 TCP 覆盖应用→上游服务、上游服务→应用、双向同时传输、粘包、拆包、大于内部缓冲区的数据、
  half-close、取消、读写超时和连接失败；线路收到的字节必须与抓包记录拼接后的已写出字节完全一致。
- 无协议包、无字段规则时透明转发仍可抓取；抓包详情只显示原始/Hex，不出现字段结构、协议视图或命中规则。
- 写失败只记录成功前缀并关联详细失败原因；读取后零写出、空流和未建立连接均不得生成伪成功记录。
- 抓包队列饱和、SQLite 暂停、UI 关闭时转发行为和吞吐不依赖抓包消费者；容量丢弃有稳定计数和可见诊断。
- 清空抓包与连接并发、停止后迟到事件、工作区切换和入口重启均不复活旧数据或串到新运行代次。
- 前端列表、筛选、分页、详情关闭/焦点恢复和窄窗口布局覆盖透明转发；定向 Rust/TypeScript 测试及
  受影响覆盖率门禁通过后，再做真实客户端与 Windows 产物验证。
